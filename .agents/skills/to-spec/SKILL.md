# Feature Definition to Technical Specification

## Activation Contract

Use this skill to hand an approved feature definition to an authoritative technical specification. It owns readiness validation and synthesis, not product discovery, a second feature interview, implementation, ticket slicing, or publication. Return missing definitions to their responsible skill rather than silently filling them.

## Readiness Gate

Before drafting, verify that the feature is identified; the current execution-scoped definition package and review handoff are available; the brief and required context exist; prototype status and confirmed disposition are explicit when used; scope, scenarios, dependencies, decisions, assumptions, and out-of-scope behavior are present; shared capabilities, comparison evidence, deviations, and risks are recorded; applicable consumer contracts and available authority evidence are valid; and each generated Domain Authority Handoff and read-only authority review is consumed when present. Either missing generated authority artifact is admissible separately only when functional and semantic decisions are closed and remaining criteria are met; record the evidence gap. Also require a `feature-review` report for the current package and review handoff with no blocker or undisposed warning.

Report each absence or contradiction and return it to `feature`, `prototype`, `feature-review`, or the owning authority. A missing generated authority artifact alone does not block readiness; a present but malformed, blocked, stale, or contradictory authority source (including a layout defect) does, until its owner resolves it (`setup-workflow` for layout, `domain-modeling` for semantic gaps). Return unresolved semantic conflicts to their owner for evidence, constraints, or canon. Send open important functional or technical decisions, with sources and constraints, to the developer, who decides within binding canon; owners do not make that decision. Resume synthesis only after resolution; a material definition change requires focused `feature-review` reverification of the current package. Do not repeat discovery. If the report does not clearly cover the current definition, return it for renewed review. Preserve `READY` or `READY WITH WARNINGS`; without either, remain `BLOCKED`. Ask only a focused question about a material ambiguity, contradiction, concurrency issue, or missing test seam that prevents synthesis. Never upgrade a blocked review.

## Synthesis

Write one complete English technical specification without changing functional decisions. Preserve each decision's resolver, source, status, accepted supersession, and distinction between business intent and canonical terminology. Include the problem, solution, user stories, implementation and testing decisions, out-of-scope and prototype decisions, approved deviations, accepted risks, dependencies and native relationships, and the final feature-review report reference.

Load the `codebase-design` skill and use its vocabulary. For every proposed structural decision, state evidence, reason, and necessity; label it mandatory or a recommendation. A choice is mandatory only when an authority rule, accepted decision, contract, or indispensable dependency requires it; cite the source and necessity. Preserve approved observable behavior and applicable binding constraints, stating each mandatory constraint's source and reason. Recommend a structural choice only when evidence shows the need it serves; propose the highest useful existing seam when useful without making a recommendation obligatory. For a material ambiguity or contradiction against binding authority or approved behavior, present the conflict, sources, and constraints to the developer, who decides important choices within binding canon. Owners supply evidence, constraints, and canon, not decisions. Return unresolved owner matters for resolution and focused `feature-review` reverification; do not resolve conflicts by preference or proceed unresolved. Record shared-capability invariants for implementation and ticket slicing. Specify observable behavior and tests, not stale paths or implementation snippets.

## Preparation, Publication and Handoff

`READY` and `READY WITH WARNINGS` permit publication, not publication itself. For GitHub or Linear, verify tracker read capability before preparing the preview and write capability before the first publication mutation; on either failure, report `blocked` and send no mutation request. Prepare the playbook's approval preview with destination and title, current package and review handoff, stage artifacts and roles (stable brief and report for joint `feature-review` publication, or final specification and report for `to-spec`), verdict, accepted warnings and deviations, parent and disposition, and external effects. Technical specifications are English; human-facing tracker artifacts and comments are Spanish. Preview creates no durable artifact or external mutation. Approvals follow the pull-request playbook's approval policy and approval preview; with no recorded policy, use `every-step` and [the shipped rules](../setup-workflow/assets/pull-requests.md#approval-gates-and-external-effects), telling the user once to run `setup-workflow update`.

In GitHub and Linear, a specification has one parent ticket: an issue specification is its own parent; a file specification gets a Spanish parent issue following tracker publication fields, identifying the specification by path only (never commit). Reuse one open issue matching the specification location, even without children. A closed match or multiple candidates blocks with no mutation request. Preview whether to reuse, create, or use the specification issue itself. GitLab, `local-markdown`, and `none` have no parent.

Once publication is approved wherever policy requires, or at once under `autonomous`, the orchestrator performs the mutation. For the stable brief and report from `feature-review`, apply identity, exact-match reuse, conflict-blocking, and verified read-back controls to both. Then publish the final specification and consolidated review report for the current package and handoff; this pair neither replaces nor duplicates joint publication. Before creating the specification or report, inspect durable artifacts for the same role, package, and handoff; reuse one exact match, create only a missing artifact, block multiple matches or conflicting content, and verify read-back. Publish the GitHub or Linear parent too. Reinspect parent equivalence before creation; any change from the preview requires a new approval preview. Create a file specification's parent after its read-back. Set `PUBLISHED` only when every applicable artifact has verified read-back for the current package and handoff. Partial, conflicting, duplicate, malformed, stale, blocked, or unread-back publication remains `BLOCKED`; do not hand off. Keep drafts and intermediate reports as working state. A material correction invalidates the prior review; return to the definition block and reuse review and publication controls, preserving durable artifacts.

Hand `to-tickets` the published specification and review, parent identity in GitHub or Linear, current package and review handoff, verdict, applicable prototype branch and commit, UI contract, confirmed disposition, decisions, deviations, accepted risks, dependencies, native relationships, conditions, and invariants. If ticket slicing finds a definition defect, return it here without editing the published specification.
