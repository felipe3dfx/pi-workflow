# Behavioral Scenarios

The decision table this skill implements, as the conformance view of the normative detail in [runtime-contract.md](runtime-contract.md). Each row states a repository condition and the outcome the contract requires, so a run can be checked against something falsifiable rather than against an impression.

| Scenario | Repository state | Required outcome | What must stay untouched |
| --- | --- | --- | --- |
| Missing instructions | Root `AGENTS.md` is absent. | Stop, offer either the harness's native initializer or a minimal `AGENTS.md`, and await confirmation. | Everything. No file is created. |
| Candidate cardinality | A recorded value has zero, exactly one, or multiple verified candidates. | Zero awaits confirmation, one proceeds with the sole candidate, and multiple await selection. Never choose by default. | Everything, until the confirmation arrives. |
| Dependent capability counting | One governing value carries candidates, or a stated absence removes them, for more than one capability. | Count candidates per governing value and give every dependent capability the resulting state; count a capability no governing value covers on its own. | Nothing else. |
| Linear branch convention | The tracker is Linear. | Resolve the team key in Linear and record `CHILD_BRANCH_CONVENTION` as the pattern `<KEY>-<number>` with that key (`ENG-<number>`, never a literal identifier); `fix/` or `feat/` history, prefix styles, and slugs are not candidates, and a key that stays unresolved leaves the value an unresolved marker. A recorded prefix or prose value is a reported difference, never a rewrite, and a non-Linear tracker counts this value as any other. | Everything, until the approval arrives. |
| Fixed pull-request body | The pull-request playbook is about to be written, or an existing one records a body template. | The body is the three-section contract the asset ships (`## Summary`, `## Evidence`, `## Merge Danger`), with no other section added; pull-request history and a `.github/pull_request_template.md` are not candidates, and a recorded template is a reported difference, never a rewrite. | Everything, until the approval arrives. |
| Fixed mutation scope | The pull-request playbook is about to be written, or an existing one records a commit count or a ticket-closure policy. | Record that a pull request carries as many commits as needed and that no skill closes or transitions the tracker ticket; one-commit-per-pull-request, mandatory squash, and automatic ticket closure are not candidates, and a recorded policy is a reported difference, never a rewrite. | Everything, until the approval arrives. |
| Linear pull-request link | The tracker is Linear and the tracker playbook is about to be written, or an existing one records comment rules. | Record in `docs/agents/issue-tracker.md` that an append-only Spanish comment on the issue carries the pull request URL and evidence without changing issue state and that no discovered comment policy overrides it, while `pull-requests.md` cites the ticket identifier and points at the tracker playbook; pull-request history is not a candidate, and a recorded rule is a reported difference, never a rewrite. | Everything, until the approval arrives. |
| Fixed pull-request metadata | The pull-request playbook is about to be written, or an existing one records draft state, reviewer, or label policy. | Record that the pull request opens as a draft with no labels and no reviewers and that ready-for-review, labels, and reviewers are a manual human process; an observed reviewer or label practice is not a candidate, and a recorded policy is a reported difference, never a rewrite. | Everything, until the approval arrives. |
| Provider-owned review and merge | The pull-request playbook is about to be written, or an existing one records an approval policy, a review mechanism, or a merger. | Record that review, required checks, and merge belong to the pull-request provider through branch protection and destination-branch permissions, with no standing approval and no named merger; a repository's merge practice is not a candidate, and a recorded policy is a reported difference, never a rewrite. | Everything, until the approval arrives. |
| Template instantiation | Playbooks are approved and about to be written. | Every `{{PLACEHOLDER}}` is replaced with its confirmed value and the tracker template lands as `docs/agents/issue-tracker.md`, so every path in the routing block resolves. | Nothing else. |
| Approval before the first write | Every recorded value resolved to a single verified candidate, so no question was ever asked. | Present the complete proposed contract and await explicit approval. Skipping every question never skips this gate. | Everything, until the approval arrives. |
| Absent domain authority | No root glossary exists, so `docs/agents/domain.md` is recorded as the future authority path. | Record authority as absent and the capability to produce it separately. An available `domain-modeling` never makes an absent glossary read as present. | Nothing else. |
| Confirmed absent tracker | No tracker evidence anywhere, and the user confirms the absence. | Select `issue-tracker-none.md`, record the capability `unsupported`, and keep the routing block resolving. Never instantiate a service template without evidence. | Nothing else. The absence is recorded, not worked around. |
| Existing contracts | Root instructions and all owned playbooks exist, but the routing block is absent. | Detect the missing block, propose adding it, and await the user's choice. | Every existing file, including the instruction file. |
| Repository-stated absence | Root instructions state a practice does not exist, such as "there is no review process; commits go straight to `main`". | Worked example of the stated-absence rule. What the statement denies is read from the evidence, as any candidate is: here it denies the whole pull-request path, so the provider value records `none (confirmed absent)` citing it, with no question asked, and its capabilities are `unsupported`. Branching and pushing stand alone, so they keep their own counting and stay `requires-setup` where a remote is merely unconfigured. A repository stating only "there is no review process" denies less, so the provider and branch-rule values are asked; that is the rule working, not a gap. | Everything. The statement is evidence, never text to copy into a value slot. |
| Durable confirmed absence | The user confirms a value has no candidate. | Record `none (confirmed absent)` as that value. An unsubstituted token means nobody was asked, so the next run must not have to ask again. | Nothing else. |
| Repository drift on a rerun | All owned playbooks exist, and since setup the repository changed so a recorded value no longer holds, such as `quality.md` recording `make check` after the Makefile stopped defining `check`. | The script's diff, fed the recorded values, still reports IDENTICAL: form is intact, and form is all the script measures. The contradiction is found by discovery and judged by the model: the command the value names no longer exists, which is a contradiction, unlike a new candidate standing beside a settled value, which is not. It is part of the delta, reported beside the preserved value, and corrected only by an approved `update` carrying the new value. Wording divergence between rediscovered evidence and recorded evidence prose is never a difference. | Everything, until the approval arrives. |
| Escaping destination | `docs/agents` or `AGENTS.md` is a symlink resolving outside the repository. | Every write subcommand refuses before writing anything, the run reports the refusal, and the remedy belongs to the user. A run without an interpreter performs the same check from the same sentence. A symlink resolving inside the repository is fine; the invariant is containment, not symlink absence. | Everything, including the symlink itself. |
| Unchanged rerun | Rediscovery matches every existing owned contract. | Report no drift, ask nothing already recorded, request no approval, and propose nothing. | Everything. The run writes nothing at all. |
| Hand-edited contract | The routing block and a quality playbook differ from the proposed contract. | Report both differences beside the proposed change. `routing --append` is a no-op beside a matching block and refuses beside a differing or malformed block, so a second block is never appended; `--check` reports the divergence. An approved `update` rewrites the playbook from the current asset and the recorded values, and leaves the routing block untouched. | The routing block, byte for byte, until the user acts. |
| Partial contract update | An owned playbook calques the contract's sections, and the contract changed. | An approved `update` re-renders the current asset from the already recorded values and rewrites the file: a section the contract defines and the file lacks is added, and a recorded value the repository contradicts is corrected only through the new value. The rewrite replaces the body of each section the contract owns, so a line the consumer added inside one is not preserved; local text belongs outside the contract's sections. | Every file not approved, byte for byte. |
| Foreign section on a rerun | An owned playbook carries a section the contract does not define. | `update` refuses that file, names the section, and writes nothing for it; other approved files in the same batch still update. The remedy is the user's: move the content to a file the contract does not own, or hand-edit. The guard compares headings, so it does not see a repeated contract heading or one hidden inside an unclosed fence; the rewrite replaces those, and the approved diff is the net. | The refused playbook, byte for byte. |
| Marker over a recorded value | A values file gives `<marker>` for a token whose value an existing playbook already records. | `update` refuses that file, names the token, and writes nothing; a recorded value is never degraded to an unresolved marker. The script matches the token's contract line and its literal prefix, so it sees a value recorded on the same line or behind an unchanged prefix; any other rewrite rests on the exact diff the user approves. | The playbook, byte for byte. |
| Write without approval | A file to create, update, or append is not named by an approval. | The command reports it and writes nothing; the script writes no file its approval does not name, and `routing --append` requires `--approve AGENTS.md`. `render` creates only approved files, so deleting a playbook and recreating it is not a path around the guard. | The file, byte for byte. |
| Approval binds the diff | A playbook differs and will be written. | The proposal's exact diff is `update`'s own output without an approval; the write re-runs the same command over the same values file and assets, so the approved bytes are the written bytes. | Every byte not in that diff. |

Four questions are settled as out of scope and stay that way: the vocabulary for naming disabled workflow phases, which is free prose until the workflow skills define phases; recording `supported` for a command discovery never executed, which is the price of the no-side-effect rule; choosing a working base when several branches qualify, which is a proposal and never gates; and what the conversation about unrelated `docs/agents/` files resolves to, which is the migration itself. A finding against any of these is not a defect.

No row permits a write without approval, and every row that detects a difference preserves the existing value and waits. A run that writes over an existing playbook without an approval naming it, or that resolves a difference on its own, has left the contract regardless of how reasonable the result looks.
