# ADR 0013: Child command policy for git and gh

## Status

Acceptance: approval and merge of the introducing PR.

## Decision

A child session reads `git` and GitHub state on its own. Commands that mutate the repository or the remote, or publish, stay with the parent. For both `git` and `gh` the policy is an allowlist of reads: everything not listed is refused. It applies the same way whether Jev routing is on or off.

The child's `bash` runs each command after a harness-owned prefix, set through the bash tool's `commandPrefix` option, that defines the shell functions `git` and `gh`. The prefix is two lines: `unalias git gh 2>/dev/null || :`, then the guard on one line. The child reads `shellCommandPrefix` and `shellPath` from the parent's settings: the parent session's directory and its project trust decision, so a trusted project's settings apply as they do to the parent's `bash`. The child's own directory is not a settings source, because it carries no trust decision. The functions are POSIX shell code, so the user's prefix and the guard run with `shellPath` only when its file name is `bash`, `zsh`, `sh`, `dash`, `ksh`, or `mksh`. Otherwise, such as fish, the child runs the guard alone under Pi's default bash and skips the user's prefix, whose syntax belongs to that shell. With no `shellPath`, the prefix and the guard run under Pi's default bash. The user's prefix runs first, followed by the two guard lines. The line numbers in a bash error therefore point 2 + N lines below the command's own line, where N is the line count of the user's prefix, or 0 without one. The `unalias` line stands alone because bash expands aliases when it parses a line, so a user prefix that enables `expand_aliases` and aliases `git` or `gh` would otherwise break the function definitions. When the child's directory cannot be resolved to its physical path, the launch fails with that error, because the guard's scope is that path. The functions are not exported and are POSIX `sh`; their helpers carry a `__pi_workflow_` prefix and keep their variables in a subshell. They expand no unset variable and no line of the prefix fails, so a user prefix with `set -u` or `set -e` does not abort them. A function decides from the command words it receives and the working directory. When it allows a command, it runs the real program with `command git "$@"` or `command gh "$@"`. When it blocks one, it writes this message to standard error and returns 126:

"`<command>` is reserved for the parent. Continue without it and list the exact command in your result; do not ask the parent to run it."

`<command>` is `git <subcommand>`, `git <subcommand> <verb>`, `git <global option>`, `git -c`, or `gh <group> <verb>`, and `gh <group>` when there is no verb. The message names no role and does not invite `ask_parent`.

The functions guard only the model's own command line, including its pipelines, subshells, and command substitutions. Processes it starts, such as npm scripts, `git` hooks, husky, lint-staged, tests, `sh -c`, and `xargs`, run the real programs. This replaces the `PATH` stubs of ADR 0011, which every descendant inherited, so a child's `npm run check` or commit hook failed with exit 126 on its own `git` calls.

The `git` function blocks only when the physical working directory (`pwd -P`) is the child's worktree root or inside it. Elsewhere, such as a temporary repository a test creates, it runs the real `git`. It reads the leading global options and allows only `-C <dir>`, `--no-pager`, and `-c <key>=<value>`, separate or attached (`-ccolor.ui=never`), whose key, in any case, is `color.*` or `core.quotePath`. Any other `-c` key is refused as `git -c`, because keys such as `alias.*`, `core.pager`, `core.editor`, `core.sshCommand`, and `diff.external` run commands. Every other global option is refused as `git <option>`, such as `git --git-dir`, `git --work-tree`, `git --config-env`, and `git -P`. It allows these subcommands whole: `status`, `diff`, `log`, `show`, `blame`, `grep`, `ls-files`, `ls-tree`, `ls-remote`, `cat-file`, `rev-parse`, `rev-list`, `merge-base`, `describe`, `shortlog`, `name-rev`, `for-each-ref`, `show-ref`, `show-branch`, `whatchanged`, `range-diff`, `diff-tree`, `diff-files`, `diff-index`, `cherry`, `count-objects`, `check-ignore`, `check-attr`, `var`, `version`, and `help`, and `git` with no subcommand. For `reflog`, `stash`, `worktree`, `remote`, `submodule`, and `lfs` it reads the next word that is not an option and allows only `reflog` with no verb or `show`; `stash list` and `stash show`; `worktree list`; `remote` with no verb, `show`, and `get-url`; `submodule` with no verb, `status`, and `summary`; and `lfs ls-files`, `status`, `env`, and `version`. Any other verb is refused as `git <subcommand> <verb>`, or `git <subcommand>` without one. `branch` runs bare or with `--show-current`, `-a`, `--all`, `-r`, `--remotes`, `--list`, `-l`, `-v`, `-vv`, `--verbose`, `--contains`, `--merged`, and `--no-merged`; those last three take a commit, and a pattern is allowed only after a listing option, so a branch name to create is refused. `tag` runs bare or with `-l` or `--list` and its patterns. `config` runs only with `--get`, `--get-all`, `--get-regexp`, `--list`, or `-l`, optionally with `--show-origin`. Any other option or word of those three is refused as `git branch`, `git tag`, or `git config`. Every other subcommand is refused, including `git credential`, `git send-pack`, `git fast-import`, `git imap-send`, and `git svn`.

The `gh` function decides from any directory, because `gh` acts on the remote. It finds the group and the verb by skipping `-R` and `--repo` with the next word, and `--repo=<value>`. Any other option before the verb refuses the command as `gh <group>`, because `gh` may read the next word as that option's value: in `gh pr --subject view merge 12`, `gh` runs `merge`, not `view`. Options after the verb, as in `gh pr list --state open`, are not read. It allows the verbs `view`, `list`, `diff`, `checks`, `status`, `watch`, and `download` in any group except `auth`, the whole `search` group, `repo clone`, `help`, and `gh` with no group, including `gh --help` and `gh --version`. Everything else is refused, such as the whole `gh auth` group, including `gh auth status`, because it prints credentials; `gh api`, `gh pr create`, `gh pr checkout`, `gh pr revert`, `gh repo set-default`, `gh repo autolink create`, and `gh project item-add`. Both policies are allowlists because review rounds of the denylists kept finding mutating subcommands, nested or unknown mutating verbs, and option values read as the verb; an allowlist fails closed.

Supersedes: ADR-0011. This reverses its clause, accepted in #166, that the child's `bash` runs `git` and `gh` unchanged while Jev routing is on, and replaces its `PATH` stubs with shell functions. A Jev-on child no longer commits or pushes.

## Considered Options

- Keep ADR 0011: block all `gh`, and all `git` inside the worktree, only while Jev routing is off. Rejected: children asked the parent for plain reads such as `git status` and CI logs, and the Jev-on branch let a child commit and push.
- A denylist hardened by session evidence for `git`. Rejected: review rounds kept finding mutating subcommands it missed, such as `git send-pack`, `git fast-import`, and `git lfs migrate`, and global options that run commands, such as `-c core.pager` and `--config-env`.
- An allowlist of read commands for `git`, the same fail-closed model as `gh`. Chosen: a missing read becomes a refused command the child lists in its result, which costs less than a mutation that runs.
- A denylist for `gh`. Rejected: three review rounds kept finding nested or unknown mutating verbs, such as `gh pr revert`, `gh repo set-default`, and `gh repo autolink create`, and option values read as the verb.
- An allowlist of read verbs for `gh`. Chosen: it fails closed.
- Keep the `PATH` stubs. Rejected: every descendant inherits `PATH`, so the stubs refused the `git` calls of hooks, npm scripts, and tests that the child ran legitimately.

## Consequences

A child runs `git status`, `git diff`, `git log`, `git show`, and `gh` reads without asking. A blocked command fails non-zero, and the child lists it in its result for the parent to run. Tests, hooks, and tools keep working, including `npm run check` inside a child, because they run outside the model's command line or outside the worktree.

Deferred until a real session shows the need: `gh` alias resolution; the `GIT_DIR`, `GIT_WORK_TREE`, and `GIT_CONFIG_*` environment overrides; absolute-path invocations of `git` or `gh`; the physical-path comparison on Windows and Git Bash, where `pwd -P` and the resolved worktree path use different forms; guards for the shell programs `rm` and `find`; and SQL.

Accepted risks:

- R1: options of allowed `git` reads that run a program, such as `git grep -O<command>` and `git ls-remote --upload-pack=<command>`, go through like any descendant process, and both functions let `gh` aliases and extensions invoked with an allowed verb, environment overrides, absolute paths, `command git` and `command gh`, descendant processes such as `sh -c`, `xargs`, and npm scripts, and `git -C <worktree>` or `--git-dir` invoked from outside the worktree through. A user prefix that redefines `unalias`, `command`, or the guard functions is out of scope. The functions guide the model; they are not a security boundary. In-process tools such as the `codegraph` tool do not go through them.
- R2: `git` reads outside the allowlist are refused, such as `git bisect log`, `git notes list`, `git sparse-checkout list`, `git fetch`, `git config get`, `git --version`, and `git -c` with other harmless keys. The `gh` allowlist refuses reads outside it, such as read-only `gh api`, `gh repo autolink list`, `gh variable get`, top-level `gh status`, `gh browse`, and help forms after a group such as `gh pr --help`, while its verbs allow reads in sensitive groups, such as `gh secret list` and `gh release view`. Harden or relax only with evidence.
