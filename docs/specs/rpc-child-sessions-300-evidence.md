# #300 implementation evidence

## Scope and environment

- Ticket: #300, "Apply authorization and signed commits inside the child"; branch `300`, merged with `296-rpc-children` at `f3086d9` (after #298, #299, #301, #303 and #304).
- Specification: `docs/specs/rpc-child-sessions.md`, sections 4.4, 5 and 12; ADRs 0013, 0020, 0021 and 0022.
- Host: Linux 7.2.8, standalone Pi 1.4.0 on `PATH`. No macOS run was made.
- Real-binary tests use the installed `pi`, a scratch `PI_CODING_AGENT_DIR`, the local scripted model endpoint (`test/support/model-endpoint.mjs`) and the SSH-signed repositories of `test/support/signed-checkpoint.mjs`. Without `pi` on `PATH` they skip with "Pi is not installed on PATH, so the real-binary RPC child checks cannot run."

## What changed

- Operational path (ADRs 0013 and 0020), the production path: the launch passes the checkpoint grant itself, not a boolean, in `--pi-workflow-child`. A granted worker's runtime registers `checkpoint` with that grant, and its guarded bash points `git add` and `git commit` to the tool. Each checkpoint reaches the parent in a `checkpoint {id, checkpoint}` frame. The tool waits for the parent's acknowledgement before it returns, so the checkpoint is recorded before the run can end. A lost acknowledgement never turns a made commit into a tool error. `createCheckpointTool` and `installActionAuthorization` now await their `checkpointed` callback.
- Contextual path (ADRs 0021 and 0022), installed but unadopted: it is used only when the host passes `authorization`, as `contextualWorkflowSources` does, and production never does. In that case the runtime gets `contextual: {active}`. It installs the unchanged `installActionAuthorization` in the child, so every `tool_call` the child dispatches is evaluated there, nested script calls included. The host's `authority`, `classify` and `onDecision` stay in the parent and answer `policy {id, method, value}` frames. A withdrawn frame aborts the signal the parent hands them. Consultation goes through the existing `ask` frame with the consultation question, which now lives in `child-runtime.ts` and is shared with the SDK adapter. The final system prompt snapshot comes from the public `context_with_system` event, which replaces the SDK-only `bindSession`.
- The contextual child keeps the tool set it had in process. It has a plain `bash` with the parent's shell settings (`createConfiguredBashTool`), the contextual `ask_parent` description, `report_result` for every role and the contextual `checkpoint`. It gets no `--tools` allowlist, adds `builtin:tool-search` and the common sources selected by path, and activates the same default tools (`defaultActiveTools`). The parent rebuilds `pendingAuthorizations()` from the child's `pi-workflow-authorization` entries (`entry_appended`).
- `ActionAuthorization.authority` now takes `Pick<ExtensionContext, "cwd" | "signal">`, which is all a host can receive across a process boundary.
- The old refusal "Contextual authorization is not available to RPC children." is gone. Common tool factories are in-process functions, so a launch that selects them is refused: "Common tool factories cannot load in a child process; select the common tool sources by path."

## Open gaps

- A contextual RPC child has no child toolbox: the SDK child loaded `childToolbox` and could launch grandchildren. In a child process that toolbox would need the parent's seating state from `shell.ts` and an authorization relayed one more level. The grandchild launch therefore is not available to a contextual RPC child.
- Common tool factories (`CommonToolSources.factories`) cannot cross into a child process, so a contextual launch that selects them is refused. Selected paths still load.
- The host's `authority` receives only `cwd` and an abort signal, not the child's full `ExtensionContext`.
- `pendingAuthorizations()` is rebuilt from the child's recorded `pi-workflow-authorization` entries. A held proposal still in consultation when the child process dies is not reported, because its entry is written only after the decision.
- `test/contextual-authorization.test.mjs` still exercises the contextual path through the SDK adapter (`createPiChildSession`); it is not ported to RPC children.
- No macOS evidence was produced on this Linux host.
